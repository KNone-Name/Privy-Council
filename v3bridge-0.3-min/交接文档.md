# v3bridge 0.3 —— 交接文档

> DLL 注入式的外部控制层，用于 Victoria 3。不改游戏文件、不装 mod。
> 本文是**唯一总览**；建造链路的深度逆向细节见 `逆向-建造注册.md`。

---

## 0. 一句话

注入一个 DLL，通过**读写控制文件**让外部程序能查询世界状态、建造建筑、读写生产方式；
所有写入都锁死在玩家自己的国家上，游戏更新后能自行重新定位关键函数。

当前状态：**建造、查询、PM、队列全部可用**，读档/新游戏/切国家都不会崩。

本文对应 **v3bridge 0.3 / Victoria 3 1.15.1**；包内 DLL SHA256 以 `bin/v3inject.dll` 为准。

## 2. 怎么跑

```powershell
# 1. 启动游戏，进入存档
# 2. 注入
#    injector 自己要的是“DLL 的绝对路径”；相对路径是 v3ai 配置层负责解析的。
$dll = (Resolve-Path .\bin\v3inject.dll).Path
.\bin\injector.exe victoria3 $dll

# 3. 等就绪：日志出现 capabilities: ... on，并响两声
Get-Content .\bin\v3inject.log | Select-String "capabilities"
```

> v3ai 的 `service.injector` / `service.dll` 可以写相对路径，
> `ServiceManager` 与 `host_agent.py` 会按工作区根目录解析成绝对路径后再传给 injector。
> 直接手跑 `injector.exe` 时仍建议传绝对 DLL 路径，因为 injector 按目标进程的 CWD 解析。
>
> **DLL 的控制文件写在 DLL 自身所在目录。** v3ai 使用 `_archive/v3inject.dll`，
> 且 `executor.bridge.dir` 也是 `_archive`；不要把 DLL 放在 `_dist/bin` 却让 bridge 去 `_archive` 读。
> 发布包的 `bin/` 是手工注入用；接入 v3ai 时把 DLL 放到 bridge 目录，或把 bridge.dir 指到 `bin/`。

就绪后同目录会出现 `world.current.txt`（世界状态）和 `player.current.txt`（玩家国家 id）。

### 控制文件协议

**写一个 txt → DLL 处理后把它改名成 `.done.txt` → 读结果文件。**

这个「改名」就是完成信号：文件还在 = 没处理完；变成 `.done.txt` = 处理完了。
外部程序只要轮询 `.done.txt` 出现即可，不需要猜时间。
新增的 `pmscan` / `pmfix` / `usecap` / `findptr` 也遵循同一套 `.done.txt` 机制。

| 输入 | 内容 | 输出 |
|---|---|---|
| `requests.txt` | `<州id> <建筑键> <等级>` | 日志；返回值 = 队列增量 |
| `query.txt` | `building <建筑键> [all]` | `states.csv` |
| `pms.txt` | `<州id> <建筑键>` | `pms.csv` |
| `pmm.txt` | `<州id> <建筑键> <pm键>` | `pmm.result.csv` |
| `queue.txt` | 任意 | `queue.csv` |
| `pmscan.txt` | `<建筑键> [all]` | `pmscan.csv` |
| `pmfix.txt` | `<目标州> <建筑键> <参照州> [dry]` | `pmfix.csv` |
| `requestcap.txt` | 捕获到的请求对象原始字节（自动写） | 供 `usecap` / 分析用 |
| `usecap.txt` | `<州id> <建筑键> [等级]` | `usecap.done.txt` + 日志 |
| `findptr.txt` | `<十六进制地址>` | `findptr.csv` |
| `parambytes.txt` | 可选的参数模板 | 建造时作为 param 模板 |
| `bdump.txt` | `<州id> <建筑键>` | `bdump.csv`（对象前 0x200 字节） |
| `peek.txt` | `<十六进制地址> <数量>` | `peek.csv` |
| `probe.on` | 空文件 | `buildprobe.log`（硬件断点探针） |
| `watch.txt` | `<州id> <建筑键> [秒]` | 在 PM 数组上设写断点 |
| `force_unknown` | 空文件 | 强制走签名路径自测 |
| `unload.flag` | 空文件 | 卸载 DLL |

**注意**：
- `unload.flag` 是一次性的，DLL 读到即删除。不要在注入前留着。
- `watch.txt` 用完必须删；它挂在建筑的 PM 数组上，世界切换后会失效（v150 起会自保护，但别留着）。
- 建造失败返回 0，成功返回队列增量（可能 >1）。

## 3. 架构

```
游戏主线程（消息泵）
   └─ 我们挂的 PeekMessageW 等消息 API → 每帧调用 PumpWork()
        ├─ RunWorld()      判定主菜单/存档、计算世界状态
        ├─ 各指令处理        控制文件 → 引擎调用 → 结果文件
        └─ 世界切换静默期     读档/选国家期间不做任何引擎操作

独立线程（DLL 自己创建）
   ├─ Bootstrap          解析 PE、定位函数、启动其余线程
   ├─ TypeScanThread     扫堆建立建筑类型表（633 键，约 20~40 秒）
   └─ PlayerScanThread   扫堆定位 CJominiPlayer 对象
```

**为什么用消息钩子驱动**：游戏是消息泵模型，我们必须在它的线程上调用引擎函数，
否则引擎内部的锁和线程假设都会被破坏。钩住 `PeekMessageW` 等多个 API 保证即使窗口
不活跃也能跑到。

**为什么扫堆放在独立线程**：一次全表扫描要几秒到几十秒，放在泵线程会让游戏卡住。

## 4. 关键技术点

### 4.1 故障保护（最重要）

引擎调用随时可能因为世界切换而踩到悬空指针。所有引擎调用都走这层：

```cpp
t_inCall = 1;                      // thread_local
if (__builtin_setjmp(t_jmp) == 0) {
    ...调用...                      // 可能抛 AV
    t_inCall = 0;
} else {
    t_inCall = 0;                   // 已恢复
    ...降级处理...
}
```

VEH 处理器只接管 `t_inCall` 为真的访问冲突，然后 `longjmp` 回调用点；
其余异常一律 `EXCEPTION_CONTINUE_SEARCH` 放行给游戏自己。

**必须遵守的两条：**

1. **`setjmp`/`longjmp` 之间被修改的变量，如果要在跳回后使用，必须声明 `volatile`。**
   否则值不确定——曾经因此返回垃圾指针、无保护解引用、把游戏带崩。
2. **异常处理器里禁止文件 IO / 堆分配。** 曾经在处理器里 `fopen` 写日志，
   撞上锁就死锁/崩溃。现在处理器只拷贝到内存 + 设脏标志，文件由泵线程写。

### 4.2 世界切换静默期

读档和「新游戏选国家」时，世界对象正在销毁重建。此时任何引擎调用都可能踩空。

- 检测到「主菜单 ↔ 存档」切换 → 记录时间戳
- **只要州数量还在变化，静默期就一直往后推**（不是固定几秒）
- 静默期内**完全不碰引擎对象**：不扫玩家、不扫类型、不处理指令

### 4.3 玩家对象定位

引擎在读取档时创建 `CJominiPlayer`，位于较新（高地址）的内存。定位方式：

1. 用已知 vtable 在堆里**倒序**扫描（新分配的对象在更高地址，通常几秒内命中）
2. 命中后读 `+0x58` 得到国家 id，校验范围 `(0, 65535)`

**坑**：`CCountry+0x18` 不是国家 id（实测 31995，而真实 id 是 10）。不要用它做交叉验证。

### 4.4 建造（核心能力）

在栈上构造请求对象，调用引擎的命令分发函数：

```
req-build(0x1085B90, opcode=0x30CA)
  → request->vtable[0] = wrapper(0x8C2410)
  → BuildCommand(0x8C24B0)
  → order-build(0x968397)         ← 脚本效果，做完整初始化
  → queue-insert-gov(0x95C770)
```

请求对象 0x50 字节：

```
+0x00  请求虚表（RVA 0x46B5048，运行时还会校验）
+0x08  国家 id          u32
+0x10  州 id            u32
+0x18  CBuildingType*
+0x20  param 块（0x18 字节，全 0 即可）
+0x38  levels (u32) | arg6=1
+0x40  arg7 = 0xFFFFFFFF
+0x48  ctx（全局，RVA 0x5C0DCA8 里的值）
```

**关键结论**：`param` 全 0 完全没问题。曾经以为必须带运行期 ID，是误判。

0.3 额外提供“请求模板”后备：

- 打开 `probe.on` 后手动在 UI 建一次，`wrapper` 会捕获该类型的完整请求对象；
- 捕获结果写到 `requestcap.txt`，并按类型存入 `tpl/`；
- 后续同类型建造优先复用该模板；模板失败会自动回到合成请求；
- 可用 `usecap.txt` 手工重放一次捕获请求，用于对比/排错。

合成请求仍是主路径，模板只是为类型特例和排错服务。

**合法性前提**：煤矿等资源类建筑只能建在有对应资源的州。在没资源的州建矿，引擎会走
它自己坏掉的断言路径（未初始化日志通道 → 空指针解引用）。我们的故障保护能接住，
但该类型会被记为「本会话不可用」，不再重试。

### 4.5 生产方式（PM）

```
CBuilding + 0x1E8  数据指针（void**）
CBuilding + 0x1F0  容量
CBuilding + 0x1F4  数量
CBuilding + 0x1F8  分配器对象
```

正常建筑：数量 == 组数（煤矿 4、大学 3、工具厂 2）。
直接调旧接口创建的建筑可能只有 1 个，用 `pmfix` 从同类型建筑复制。

**改 PM**：在该建筑已激活的槽位里找「同组」的那个，替换指针（`pmm`）。

### 4.6 建造队列

```
CCountry + 0xB00   政府队列
CCountry + 0xB78   私人队列
  容器 + 0x60  数据指针
  容器 + 0x68  容量（实测 1024）
  容器 + 0x6C  数量（注意：有时只表示“当前活动项”）
  元素大小 0x48；+0x28 总点数，+0x30 剩余点数
```

**0.3 的队列读取修复**：不再只按 `count` 截前 N 条，而是按 `capacity` 扫描整段
`DATA`，用已知 `CBuildingType*`、`state_id`、`total/left` 做有效性校验。
这样 `count=2` 但实际队列有 22 项时，也能读全。

`pts_total == 0.00` **不是**「无效条目」，而是建造力还没覆盖到它，是正常的。

### 4.7 建筑类型表

引擎的类型是 `unordered_map<string, void*>`，早期能通过 DbGlobal 直接读，
1.15.1 上该全局找不到，改为**扫描整个私有堆**匹配已知 vtable。

- 状态表在堆的**高地址端**：倒序扫描 300~500 个区域就能拿全（约 20~40 秒）
- 停止条件：拿到 ≥600 键且连续 64 个区域无新键
- 不足 600 会继续扫完剩下的区域，不会静默丢数据
- 扫完写 `types.ready`（内容是键数）并响两声

### 4.8 卸载

写一个空文件 `unload.flag` 即可卸载。三处检测：泵线程的 `CheckUnloadFlag`、
watchdog 线程（不依赖游戏消息泵，泵卡住也能卸）、以及驱动里的轮询。

卸载顺序（顺序本身是正确性的关键）：

```
1. g_unloading = 1            让所有自有线程看到并退出
2. RestoreIat()               先把钩子撤掉，之后不会再有新调用进入我们的代码
3. 等 g_threadsAlive / g_inHook 归零（最多 30 秒）
4. 移除 VEH
5. Log("unloading")
6. FreeLibraryAndExitThread
```

**为什么先撤钩子再等**：如果在等之后才撤，等到归零的瞬间可能又有线程进入钩子，
接着代码段被拆走 → 踩空。先撤钩子能保证「不再有新的进入者」，再等存量退出。

**超时怎么办：中止，不强制。**

`FreeLibraryAndExitThread` 会把代码段解除映射，只要还有一条自有线程在里面执行，
就是必崩。所以超时走的是：

```
Log("unload: ABORTED - ... nothing was unmapped")
ReinstallIat()         把钩子装回去，DLL 继续正常工作
g_unloading = 0        允许以后重试
g_unloadStarted = 0
```

宁可卸不掉，也不能崩游戏。

**钩子必须可逆**：`SetIatHooks(bool)` 同时保存原函数地址和我们的 detour 地址。
早期版本 `RestoreIat` 会把槽位表清零，导致中止后无法恢复——DLL 活着但泵不再驱动，
变成僵尸。

**实测**：卸载 → 重新注入 → 建造，全部正常。卸载后 `world.current.txt` 停止更新，
重新注入后恢复更新，是判断 DLL 是否真的卸载干净的可靠信号。

## 6. 安全设计

### 6.1 写锁（数据安全）

所有写操作前必须拿到 `LockWrite(state)`：它读该州的所有者，和当前玩家 id 比对，
**不一致就拒绝**。玩家 id 未解析时**默认拒绝**（fail-closed）。

只读操作默认可加 `all` 放开范围，**写永远不行**。

### 6.2 指令挂起

玩家对象还没解析出来时，所有指令文件**留在磁盘上不处理**（最多等 30 秒），
避免拿着过期 id 去操作错误的国家。

### 6.3 启动自检

依次验证：类型表可用、玩家可解析、建造函数可用、PM 读写可用、队列可读。
**任一项失败就把对应能力关掉**，并在 `capabilities:` 行里体现。

这既是安全网，也是抗更新的主要手段。

### 6.4 非法建造记忆

某建筑类型一旦让引擎走了断言路径，本次会话内拒绝再次尝试，日志明确说明原因。

## 7. 抗更新

**核心变化**：指纹不匹配不再罢工，改为「用签名自己找，找到多少用多少」。

| 需要的东西 | 怎么找 |
|---|---|
| ResolveState / ResolveCountry | 签名扫描。两者通配后**签名完全相同**，靠 wrapper 的调用顺序区分：call[0]=State、call[1]=Country、call[2]=BuildCommand |
| BuildCommand | 签名扫描 + wrapper call[2] 交叉验证 |
| wrapper / req-build | 各自的签名（wrapper 40 字节无通配；req-build 44 字节通配尾部 rel32） |
| 请求对象虚表 | 运行时扫数据段：找「第 0 项 == wrapper 且 +0x30 项落在 .text」的指针表 |
| ctx 全局 | 读记录 RVA 后校验：对象可读、首字段是虚表、**虚表第 0 项**在 .text。不合格就禁用建造能力 |
| 注册表全局 | 从 resolver 前导码推导 `48 83 EC 58 \| 48 8B 05 disp32` |

### 自测

放空文件 `force_unknown` → 强制不信任所有记录地址。

实测结果（全部靠签名恢复）：

```
call[0] -> 0x983660  ResolveState
call[1] -> 0x983A00  ResolveCountry
call[2] -> 0x8C24B0  BuildCommand
request vtable -> rva 0x46B5048
ctx -> 0x2238C7E0010 (vt ok)
capabilities: build=on pm=on player=on queue=on
```

四个 RVA 与记录值完全一致，建造链路实测跑通。

### 边界

**能自动恢复**：函数地址、注册表全局、请求虚表、ctx。

**不能**：数据结构偏移（§5 那张表）。这些是语义约定，签名找不回来。
实测 1.15.0 → 1.15.1 这些偏移**一个都没变**，所以小版本更新大概率无事。

## 8. 编译

```powershell
$g = "D:\msys64\ucrt64\bin\g++.exe"

# DLL
$a = @("-std=c++17","-O2","-shared","-static",
       "-o","v3inject.dll","v3bridge.cpp",
       "-Wl,--kill-at","-luser32","-lgdi32")
& $g @a

# 注入器（静态、单文件）
& $g -std=c++17 -O2 -static -o injector.exe injector.cpp
```

**`-Wl,--kill-at` 必须作为独立数组元素传入**，写成一整串会被 PowerShell 解析掉。

## 9. 排错手册

| 现象 | 原因 / 处理 |
|---|---|
| `LoadLibraryA -> 0x0` | injector 收到的不是绝对 DLL 路径；v3ai 配置里的相对路径会由 ServiceManager/host_agent 先解析成绝对路径 |
| 刚注入就 `unloading` | 目录里有残留的 `unload.flag`（一次性，DLL 会自己删） |
| `capabilities: build=off` | 自检没过：看上面几行哪一项失败 |
| `defer: holding commands` | 玩家对象还没解析出来，等 30 秒或检查是否在主菜单 |
| `build: refused - ... already faulted` | 该类型本会话内已触发引擎断言，通常是州没有对应资源 |
| `FAULT av` 出现在建造日志 | 非法建造，已被接住；游戏没事 |
| 类型表扫不完 | 正常是 20~40 秒；听到两声提示音即为完成 |
| 日志出现 `settling after a transition` 反复 | 世界还在重建，我们在等，正常 |

## 10. 踩过的坑（都修了，但要记住）

1. **在异常处理器里写文件** → 注入即崩。处理器只允许拷贝内存 + 设标志。
2. **`setjmp` 后的非 volatile 变量** → 值不确定，曾返回垃圾指针导致游戏崩溃。
3. **世界重建期间扫堆** → 读档崩溃。现在有自适应静默期。
4. **`watch.txt` 不删** → 每秒重跑一次查询，世界切换时踩空。现在找不到就消费掉文件。
5. **把 `pts_total=0` 当成无效条目** → 实际是建造力未覆盖，正常现象。
6. **用煤矿测试建造** → 一再误判为"参数不对"，其实是这些州没有煤。
7. **硬件断点不设 RF** → 原地无限重入，函数一条指令都不执行。
8. **对运行中的线程 `SetThreadContext`** → 静默失效，必须挂起线程。
9. **命中计数器不清零** → 超过上限后再也不记录，抓包全是空的。
10. **数据断点 DR7 编码写错** → 断点不生效。
11. **虚表当成必须在 `.text`** → 虚表在 `.rdata`，只有虚表第 0 项才是代码。

## 附：设计原则

> **能失败就失败，不要猜。**
>
> 猜 `+0x58` 是注册表索引 → 差点让整个写路径静默失效；
> 猜 `CCountry+0x18` 是国家 id → 把正确对象拒了 23 秒；
> 猜「建筑存在就是建造成功」→ 队列空着却报成功；
> 猜「param 必须带运行期 ID」→ 被煤矿的假阴性骗了一整晚。
>
> 所有判据只用**实测过**的关系；未验证的东西只写日志，不参与决策。
