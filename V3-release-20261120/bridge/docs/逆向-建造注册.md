# 建造注册问题：已解决（2026-11-13 凌晨）

## 结论

**不需要模板，也不需要读档。** 用「合成请求 + req-build」即可从零建造，
建筑完整初始化（所有 PM 组就绪、正确进入队列、显示 `+1`）。

0.3 仍保留可选的请求模板后备：手动建一次捕获 `requestcap.txt` / `tpl/`，
特殊类型可优先复用；它不是主路径，模板失败会回到合成请求。

之前反复失败的真正原因是：**测试用的建筑类型（煤矿）在那些州不合法**——
煤矿需要州里有煤炭资源。在没煤的州建矿，引擎会走错误上报分支，而那个分支
在未初始化的日志通道上解引用空指针（`rdi=0`）崩溃。我们的故障保护接住了它，
所以表现为「建造失败」，让人误以为是 param 的问题。

## 正确调用路径

```
req-build(0x1085B90, opcode=0x30CA)
  → request->vtable[0] = wrapper(0x8C2410)
  → BuildCommand(0x8C24B0)
  → order-build(0x968397)         ← 脚本效果，完成初始化
  → queue-insert-gov(0x95C770)
```

请求对象（0x50 字节，在栈上构造即可）：

```
+0x00  base + 0x46B5048      请求虚表（slot 0 = wrapper）
+0x08  country_id            u32
+0x10  state_id              u32
+0x18  CBuildingType*
+0x20  param 块（0x18 字节，全 0 即可）
+0x38  levels (u32) | arg6=1
+0x40  arg7 = 0xFFFFFFFF
+0x48  ctx（全局，RVA 0x5C0DCA8 里的值）
```

调用：`req-build(request, 0x30CA, nullptr, 0x3FFF)`

**param 全 0 完全没问题**——之前认为它必须带运行期 ID 的判断是错的。

## 故障的性质

崩溃地址 `0x3787360`（`mov r9,[rdi]`，`rdi=0`）在函数 `0x3787300` 里：

```
0x37873 19  test rdi, rdi
0x378731D  je   0x3787330        ; rdi 为空就走错误上报
0x3787327  mov  r8d, [rcx+0x10]
0x378732B  cmp  r8d, eax
0x378732E  je   0x3787360        ; 相等才继续
0x3787330  ...组装错误信息，call 0x406BE580
0x3787360  mov  r9, [rdi]        ; rdi==0 → AV
```

也就是**引擎的断言失败路径本身是坏的**（未初始化日志通道）。
我们的 VEH 接住后 longjmp，游戏继续运行——所以只是这次建造失败，不会崩游戏。

**推论**：DLL 侧应该先判断「该州能不能建这个类型」，避免触发这条坏路径。

## 保留的东西

- `pmfix`：从同类型建筑复制完整 PM 集合，用游戏自己的分配器
  （`建筑+0x1F8` 的对象 vtable[1] 分配）。仅在没有走通 req-build 时才需要。
- 按类型模板（`tpl/`）：可选后备，不再是主路径；`usecap.txt` 可手工重放。

| 建造操作码 | `0x30CA` |

## 探针坑（累计 10 条）

1. 必须设 RF：`ctx->EFlags |= 0x10000`
2. 必须挂起线程再 `SetThreadContext`
3. 命中计数器 arm 时清零
4. 控制文件不要在武装时消费
5. 去重键含 `rcx`/`rdx`/`r8`
6. 数据断点 DR7：`0x1D0005`
7. 断点表不能有「第 0 项用 g_buildCommand」特例
8. 数据断点的 `Rip` 是写入指令的下一条
9. 断点只在需要时挂，用完立刻撤
10. **异常处理器里禁止文件 IO / 堆分配**（曾导致注入即崩）

## 命令对象完整布局（分析用）

wrapper 收到的 `rcx` 是命令对象 + 0x18。完整对象 0x70 字节：

```
+0x00  父虚表
+0x08  u32 | u32
+0x10  u32 | u32
+0x18  请求虚表（0x46B5048）
+0x20  国家引用 / +0x28 州引用 / +0x30 btype
+0x38  param0 / +0x40 param8 / +0x48 param10
+0x50  levels | arg6 / +0x58 arg7 | u32 / +0x60 ctx
```

**注意**：把整个 0x70 字节当请求传进去会崩（v145 实测），必须以
`rcx = 请求段` 的方式调用。
## 崩溃修复记录（2026-11-14）

### 症状

1. 读档时崩溃（已修）
2. **新游戏选国家时崩溃**（已修）

### 根因一：世界重建期间扫堆（读档崩溃）

日志证据：

```
[00:26:01] world: in save (states=1024, capacity=1024)   ← 还在加载（正常是 2048）
[00:26:05] scan: start (1 candidate(s))                  ← 5 秒后就开始扫堆
[00:26:05] scan: 2689 candidate regions
[00:26:05] FAULT av ...
```

固定的 3 秒静默期太短。修复：**只要州数量还在变化，静默期就一直往后推**，
世界真正稳定后才开始任何引擎工作。

### 根因二：longjmp 后变量值不确定（选国家崩溃）

`ScanForVtInstance()` 里：

```cpp
void* found = nullptr;                 // 非 volatile
t_inCall = 1;
if (__builtin_setjmp(t_jmp) == 0) {
    ... found = cand;  break;          // 可能在中途 fault 被 longjmp 打断
    t_inCall = 0;
}
if (found) { return found; }           // ← longjmp 之后 found 的值是「不确定」的
```

C 标准规定：在 `setjmp` 和 `longjmp` 之间被修改的**非 volatile** 自动变量，
`longjmp` 之后取值不确定。于是扫描返回了一个**垃圾指针**，而调用方紧接着做了一次
**没有保护的解引用**：

```cpp
void* country = *(void**)((uint8_t*)o + 0x50);   // t_inCall 已是 0
```

此时异常处理器直接放行 → 未处理访问冲突 → **游戏进程崩溃**。

修复三处：

1. `void* volatile found`
2. 候选对象在解引用前先 `IsReadable(o, 0x80)` 校验
3. 头部 dump 循环里每次读都先 `IsReadable`

### 一并审查的其余 setjmp

其余 15 处 `__builtin_setjmp` 用法都检查过：要么故障分支直接 `return`，
要么把结果重置为 `nullptr`，不存在同类问题。

### 现在

- 新游戏 → 选国家 → 大战 → 读档，都不崩
- 建造走 `req-build(合成请求, 0x30CA)`，完整初始化

## 抗更新（2026-11-14）

### 设计原则

以前指纹不匹配就**直接罢工**，等于每次游戏小更新都要人工重新定位一遍。
现在改成：**不认识就用签名自己找，找到多少能力就用多少**。

### 相对记录地址的全部来源（都不再依赖"这个版本"）

| 需要的东西 | 怎么找 |
|---|---|
| `ResolveState` / `ResolveCountry` | 签名扫描。两者通配后**签名完全相同**，靠 `wrapper` 里的调用顺序区分：第 1 个 call 是 State、第 2 个是 Country、第 3 个是 BuildCommand |
| `BuildCommand` | 签名扫描，同时由 wrapper 的 call[2] 交叉验证 |
| `wrapper` | 补了 40 字节签名（无通配） |
| `req-build` | 补了 44 字节签名（末尾 call rel32 通配） |
| 请求对象虚表 | 运行时扫描：在数据段里找"第 0 项 == wrapper、+0x30 项落在 .text"的指针表 |
| `ctx` 全局 | 记录 RVA 读取后**校验**：必须是可读对象，其首字段是虚表指针，且虚表第 0 项落在 .text。不合格就禁用建造能力，而不是把野指针交给引擎 |
| 注册表全局（regState/regCountry） | 从 resolver 前导码推导：`48 83 EC 58 | 48 8B 05 disp32` |

### 自测开关

放一个空文件 `force_unknown` 到 DLL 目录，DLL 会**假装当前是不认识的版本**，
强制走签名路径。用来验证抗更新逻辑本身。

实测（当前版本，全部记录地址均被忽略）：

```
sig: ResolveState   unresolved (matches=2)
sig: ResolveCountry unresolved (matches=2)
wrapper: found at rva 0x8C2410, req-build at 0x1085B90
  call[0] -> rva 0x983660      ResolveState
  call[1] -> rva 0x983A00      ResolveCountry
  call[2] -> rva 0x8C24B0      BuildCommand
sig: ResolveState   recovered from wrapper call[0]
sig: ResolveCountry recovered from wrapper call[1]
request vtable: 0x... (rva 0x46B5048)
ctx: global 0x5C0DCA8 -> 0x2238C7E0010 (vt ok)
capabilities: build=on pm=on player=on queue=on
```

四个函数的 RVA 与记录值**完全一致**，建造链路完整跑通
（`wrapper → BuildCommand → order-build → queue-insert`，队列 0->1）。

### 边界：能自动恢复什么，不能

**能**：函数地址、注册表全局、请求虚表、ctx（全部靠签名/推导/校验）。

**不能**：数据结构偏移 —— `CBuilding+0xF0`（类型指针）、`+0x1E8/+0x1F0/+0x1F4`
（PM 向量）、`CCountry+0xB00/+0xB60/+0xB6C`（建造队列）、`CState+0xED8`（所有者）
等等。这些是语义约定，签名找不回来。

实测 1.15.0 → 1.15.1 这些偏移**一个都没变**。所以真实更新时最可能的情况：
小版本直接可用；大改版可能建造能用但读队列/PM 出错，那时才需要用 `re/match.py`
重新对偏移。

### 更新后的操作流程

1. 注入，看日志：`build UNKNOWN` 说明进了签名模式
2. 看 `capabilities:` 一行，哪些能力是 `on`
3. 建造能力 `on` 就基本可用；PM/队列出错再考虑对偏移
4. 想彻底确认，先放 `force_unknown` 自测一遍
