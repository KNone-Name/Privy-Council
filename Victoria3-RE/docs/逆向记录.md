## 0. 基础约定

- 定点数：金额与数量都是 i64，**÷100000**。例外：`CBuilding.cash_reserves`、
  `CPop.workforce`（原始人数）。
- `std::string`（MSVC）：`buf@+0x0 / size@+0x10 / cap@+0x18`，`cap<16` 时
  字符串内联在对象里，否则 `buf` 是堆指针。
- `std::vector`：偏移处是 `{ptr, size, cap}` 或 `{begin, end, cap}` 的**向量头**，
  元素在 `ptr` 指向的堆数组。**当内联数组读会得到空容器哨兵 `0x7FF7DFFC8DC0`。**
- 对象常有两代并存（真对象 + 旧副本/未初始化副本），判活要按字段合理性挑。
- 运行时地址 = 静态地址 − `0x140000000` + 模块基址；ASLR 每次启动都变。

## 2. 关键子结构

### 2.1 关税 / 消费税（`CCountryBudget` 尾部）

```
+0x24B0  出口关税表  {0, ptr, n, mask, 7, f32 0.9, sentinel}   0x28 字节
+0x24D8  进口关税表  同上
+0x2500  消费税商品  {ptr, u32 n, u32 cap}                     0x10 字节
+0x2498  tax_level   u32（very_low=0 … very_high=4）
```

关税表是 `mask+1` 个 `0x20` 槽的开放寻址哈希表：

```
+0x00 u32 哈希（商品名的一一对应，引擎自有哈希，算不出来）
+0x04 f32 未明
+0x08 ptr CGoods（名字在 +0x18）
+0x10 u8  关税等级
+0x12 u8  默认/上一档（7=未设置）
+0x14 u64 最后变更日期（全 FF = 从未改过）
+0x1C f32 未明
```

等级枚举**倒序**：

```
0=max_subventions  1=high_subventions  2=low_subventions  3=no_tariffs_or_subventions
4=low_tariffs      5=high_tariffs      6=max_tariffs
```

### 2.2 税率

税率不在内存里，是「税法 × 档位」的静态表
（`common/laws/01_taxation.txt` 的 `tax_modifier_<level>` 块）。

`law_per_capita_based_taxation` / `low`：消费税 20%、人头税 55%、
土地税 27.5%、所得税 7.5%。

### 2.3 收入数组 `CCountry+0x1E00`（16 × i64，定点）

已确认索引：2=人头税、3=消费税、5=外交条约、9=关税、10=政府分红。
铸币收入、条约等行不在此数组内，位置未定。

## 4. 解法要点（踩过的坑）

1. **空容器会被过滤条件吃掉**。消费税容器在没开征时是 `ptr=0 n=0 cap=0` 的
   16 个零字节；所有「n>=1」的候选扫描都会跳过它，跨国家的「非零集合」统计
   更是原理上必然漏掉。最终靠**同对象、同地址的前后逐字节对比**抓到：
   改一处 → 12 个字节变化 → 直接点名四个字。
   **穷举不到时优先换这个方法**，它和字段编码方式无关。

2. **def 出现空容器/空槽要单独处理**。关税表也有同样问题：槽里有残留，
   分不清哪些有效。

3. **注意两代并存**。同一实体常有真对象与旧副本；判活靠字段合理性
   （如 `CCountryLaw` 同组取地址最小者、`CCountryTechnologyStatus` 取 `+0x64>0`）。

4. **长字符串是堆分配的**。按裸 C 串读 `std::string` 只能读到短名，
   必须按 MSVC 布局读。

5. **vecto 头 vs 内联数组**。`CMarket.supply@0x220` 等是 vector 头，
   当内联数组读会得到哨兵 `0x7FF7DFFC8DC0`。

6. **写文件别用 `Get-Content -Raw | Set-Content`**。本文档就是这么丢的。

## 7.5 地方法令 `CDecree` 的两个坑（2026-11-12）

地方法令（`common/decrees/`）看起来简单，但踩了两个坑：

**坑一：`CDecree` 有 2 张 vtable，多数实例挂在次要表上。**
`_instances_of` 默认只用主 vtable，结果全世界只找到 **1 条**法令；
改成扫全部 vtable 后找到 **65 条**。所以 `_country_decrees` 要传
`all_vtables=True`，缓存键会变成 `CDecree_a`。

**坑二：多 vtable 时「簇内最小地址」不是对象起点。**
`cluster_count(window=0x10)` 取簇内最小地址当基址。若次要 vtable 就在 `+8`，
最小地址就不是对象起点，按 `+0x08` 读国家 id 会读到 vtable 本身，
于是**匹配结果为 0 条**（比单 vtable 时更差）。

修法：基址不盲信固定偏移，逐个试探 `a / a-8 / a-0x10 / a+8 / a+0x10`，
用「能读出 `decree_` 开头的合法类型名」自校验，取通过的那个：

```
+0x00  vtable
+0x08  国家 id（u32）      ← 基址错了这里就读成 vtable
+0x0C  州 id（u32）
+0x10  类型指针，名字在 +0x18（decree_road_maintenance 等）
+0x20  实例序号
```

**法令修正的作用域**：`decree_road_maintenance` 的 `state_construction_mult = 0.10`
正是界面「+10% 来自道路养护」的来源——所以 `state_construction_mult` 是**州级**
修正，必须**按州分组**显示，不能把各州数值相加。

## 9. 收入数组与投资池

### 9.1 `income[16]` 的索引含义

`income_taxes` / `poll_taxes` / `dividends_taxes` / `government_share_dividends`

| 槽 | 含义 | 依据 |
|---|---|---|
| 1 | 所得税 income_taxes | 73 国求和相等 |
| 2 | 人头税 poll_taxes | 287 国求和相等；界面「人头税」也对上 |
| 3 | 消费税 | 界面金额与税率档位比例验证 |
| **4** | **红利税 dividends_tax** | 大清 20,722.84 ↔ 界面「红利税 £20.6K」 |
| 5 | 外交条约 | 界面「外交条约」对上 |
| 9 | 关税 tariffs | 40 国求和相等；界面对上 |
| 10 | 政府分红 government_share_dividends | 60 国求和相等 |
| **0** | **额外收入**（来自限时修正/事件） | 法兰西 tooltip：「+2000 来自有时限的修正」 |
| 7 | 建造投资池回收（取负） | 8/8 精确 |

注意 `supply_network_manager={ }` 在存档里是**空的**，所以这条是靠相关性
推出来的，不是直接读到的。

槽 4 = 红利税由大清界面确认（20,722.84 ↔ 「红利税 £20.6K」）。

**一个差点误判的地方**：我曾在存档里统计出「735 国 dividends_taxes 全为 0」，
并据此推断红利税不存数据、它的槽位在 6/13/14 之中。实际上 dividends_taxes
块是存在的，只是 1836.1.4 的存档里各国都是**空块**——那时还没有红利税。
成因是**日期**，不是格式或解析问题。
（这个块紧跟在别的块后面、写成 `} dividends_taxes={`，按行首搜索会漏掉。）

**槽 0 = 额外收入**（additional income）。这条一度以为找不到来源：科技和法律里

法兰西的界面 tooltip 给出了答案——「+2000 来自有时限的修正」。它是**事件或决议
授予的限时修正**，所以不在科技/法律的修正表里，文件侧查不到是正常的。

### 9.1.1 「已结算」vs「实时预测」——一个曾经误判的关键点

**`income[16]` 存的是上一次周结算的值，界面显示的是下周的实时预测。**
刚读档没走过一周时，两者必然不同。

最典型的是**铸币收入（槽 8）**：读档时只有基础值 500，界面却已经算出完整金额。
大清就是这个状态——数组 500、界面 93.7K。因为大清刚研发了科技但没走时间。

这个现象一度让我误判成「铸币收入不在收入数组里」，并据此认为
「数组总和 125K 对不上界面 226K」。实际上把槽 8 换成 93,720 后：

```
数组合计  131,655.6 − 500 + 93,720 = 224,875.6
界面合计  225,920
```

**两者基本一致**，说明这个数组就是界面那 11 行收入的已结算版本，不缺项。

槽 8 的数值形态也因此解释通了：208 国恰好 500（未走时间的底数）、
62 国 550 = 500×1.1、5 国 600 = 500×1.2（带本国铸币修正的底数）；

5. **统计槽位移常量**（`0x1D50+8i` / `0x1E00+8i`）：每个槽都有出现，

### 9.6 行政力 / 建造力：修正从哪来

capacity 命令把**法律 + 科技 + 建筑生产方式**三者的修正合并，逐条溯源。

关键结构：
- 生产方式列表在 CBuilding+0x1E0（指针向量，元素名字在 +0x18，形如 pm_wooden_buildings）
- 建筑归属：CBuilding.state_id(0xDC) → CState.state_id(0x10) → CState.owner_country_id(0xEC8)
- PM 的修正在游戏文件里分 country_modifiers / state_modifiers / uilding_modifiers，
  每类又有 workforce_scaled / level_scaled / unscaled 三种缩放

实测（大清，302 栋建筑）：

| 项目 | 合计 | 游戏界面 | 主要来源 |
|---|---|---|---|
| **行政力** country_bureaucracy_add | **+11,156.500** | **+11,156.5** ✓ 完全相等 | 26 个政府行政楼 pm_horizontal_drawer_cabinets ×50/级×吞吐，加 base_values 的 +100 |
| **建造力** country_construction_add | **+22.000** | **22** ✓ 完全相等 | 3 个建造部门 pm_wooden_buildings ×2/级（12 点），加 country_gdp_construction 的 +10 |
| 地区建造力 state_construction_mult | +0.012（+1.2%） | — | 同上，0.002/级 × 6 级 |
| 每周最大建造进度 | +25.000 | — | base_values +10 / urbanization +10 / urban_planning +5 |
| 私人建造分配 | +0.250 | — | law_traditionalism |

**行政力和建造力都与游戏界面完全相等。** 这是这套工具最完整的一次闭环验证：
从 tooltip 上的一个数字，一路追到具体建筑、具体生产方式、以及游戏文件里的全局基线。

关键的两个折算约定（都经界面反证）：

1. `workforce_scaled` 的系数 = **等级 × 吞吐量**。
   北京行政楼 16 级 × 1.16 吞吐 × 50 = 928，与 tooltip 的「+928 / 18.56 的乘数」一致。
2. 全局基线在 `static_modifiers/00_code_static_modifiers.txt` 的 `base_values` 里：
   `country_bureaucracy_add = 100`、`country_minting_add = 500`（铸币 +500 基础值）、
   `country_authority_add = 100`、`country_weekly_innovation_add = 50`。
   建造力的基线不走这里，而是另一条 `country_gdp_construction = 10`（按 GDP 缩放）。

**这些数值本身读不到**：存档 449 国的 spending_variables 块（含 construction_output、
ureaucracy_income/expenses、uthority）与 CCountry 快照做了 11 种编码的比对，
**全部无命中**。RTTI 里有 CAIManager::UpdateSpendingVariables，
说明那是 AI 的每国缓存，不是 CCountry 字段。所以只能算「修正」，
拿不到「最终值」。

### 9.7 GDP：按游戏文件公式实时计算（已验证）

游戏文件（concepts_l_simp_chinese.yml:1288）给的公式：

`
GDP = Σ(生产的商品数量 × 市场价格) − Σ(生产过程中投入的商品数量 × 市场价格)
`

实现：逐栋建筑、逐个生产方式，从 goods_output_<good>_add / goods_input_<good>_add
取每级数量，按作用域缩放（workforce_scaled = 等级 × 吞吐量），再乘市场价格。

**实测（大清，302 栋建筑，市场 49）：**

`
每周 1,595,703.37   ×52 = 82,976,575
界面 GDP = 85,100,000     差 2.5%
`

商品贡献前几名：grain 28.1万 / tea 21.1万 / services 17.3万 / clothes 15.1万 /
furniture 12.1万 / liquor 11.5万 / fruit 9.5万 / wood 8.6万 / silk 5.6万 /
porcelain 4.7万 / opium 4.1万 —— 与大清的经济结构完全吻合（无任何军事工业品），
反证公式与数据链路正确。

**三国校准（2026-11-12）**：
价格口径试过三种，最终定用**本国市场统一价**（三种里最接近游戏值）：

| 口径 | 日本（界面 9.95M） | 偏差 |
|---|---|---|
| 各州本地价 | 8,189,682 | −17.7% |
| **本国市场统一价（采用）** | **9,348,689** | **−6.0%** |
| 商品基础价 | 未测（代码支持 `--base-prices`） | — |

`--out-price` / `--in-price` 可分别指定产出侧与投入侧的价格基准
（`local` / `market` / `base`），便于以后继续试混合口径。

| 国家 | 我算的年化 GDP | 界面 GDP | 偏差 |
|---|---|---|---|
| 大清 157 | 82,976,575 | 85,100,000 | −2.5% |
| 日本 18 | 9,348,689 | 9,950,000 | −6.0% |
| 俄罗斯 1 | 26,849,048 | 22,700,000 | +18.3% |
| 合计 | 119.18M | 117.75M | **+1.2%** |

偏差方向不一致（−6% ~ +18%），**说明不是缺一个统一缩放系数**；总量互相抵消到 1.2%，
说明公式结构正确，差异来自「用哪个市场的价格」或「哪些建筑计入」。
三国的界面都标 `(100.0%)`，即 GDP 全部本国拥有，**所有权不是原因**。

人均 GDP 已交叉验证：俄罗斯 22.7M÷50.1M = 0.453 ↔ 界面 £0.45；
日本 9.95M÷32.5M = 0.306 ↔ 界面 £0.30；大清 85.1M÷366M = 0.233 ↔ £0.23。

**GDP 不存储**：存档只有 gdp={ sample_rate=120 count=1216 } 的趋势块；
CCountry 里找不到（11 种编码全试过）；AI 的 spending_variables 里也没有。
所以只能算，读不到。**人均 GDP = GDP ÷ 总人口**（concept_gdp_per_capita_desc 明写），
不是独立算法——大清 85.1M ÷ 366M = 0.2325，与界面 £0.23 一致。

**五国校准与最终口径（2026-11-12 晚）**

关键发现：**`workforce_scaled` 必须按「实际就业规模」折算，不能按建筑等级（满员假设）**。
农业/种植园建筑大量等级没招满人，按等级算会把产出放大一倍以上。

| 国家 | 界面临界值 | 等级口径 | 偏差 | **就业口径** | 偏差 |
|---|---|---|---|---|---|
| 美国 | 15.8M | 32.57M | **+106%** | 15.90M | **+0.6%** |
| 俄罗斯 | 22.7M | 27.86M | +22.7% | 22.38M | **−1.4%** |
| 英国 | 24.5M | 25.06M | +2.3% | 24.72M | +0.9% |
| 法国 | 20.7M | 20.89M | +0.9% | 20.35M | −1.7% |
| 大清 | 85.1M | 82.45M | −3.1% | 84.80M | **−0.36%** |

最终口径 = **本国市场统一价 + 实际就业规模 + 只算产出商品的建筑**。
平均绝对误差从 27% 降到 2% 以内。

另外两个被否掉的口径：
- 各州本地价 → 大清 −16.7%（本地价含市场接入度折扣，GDP 不用它）
- 含全部建筑（把政府行政楼/兵营的投入也扣掉）→ 系统偏低 3~6%，
  因为这些建筑消耗纸张木材却不产出商品

**又一个「两代对象」的坑**：CMarket 的两个实例 market_id 都是 49，
但陈旧副本的 +0x6F0 价格表是 ptr=0 cnt=0，真对象才是 cnt=54。
按 market_id 查表必须校验价格表有效性，否则读到空表。

### 9.8 想从二进制里找 GDP 公式：四次尝试全部失败（原因已查明）

GDP 的定性公式已从本地化拿到（见上一节），但**缩放约定**（PM 注释里的
`# x30`）只能从代码确认。四次静态尝试全部失败：

| 尝试 | 方法 | 结果 |
|---|---|---|
| 1 | 按预算数组位移常量搜访问器 | 命中别的类（unique_ptr 赋值、虚函数调用），全是误报 |
| 2 | 按字符串 xref（248 个含 gdp 的串） | 只有 1 个函数引用，且是销毁 thunk |
| 3 | RTTI 虚表（`CTickTask_UpdateCachedRankingsAndGlobalGDP` 等） | 虚表里全是 JUMPOUT 析构/调整 thunk，逻辑在非虚方法 |
| 4 | 按公式常量 `2000000` / `0.2` / `0.8` 定位 | `.text` 里 3 处是字节巧合；`.rdata` 里 0.2/0.8 属于全局字面量表；`2000000` **全文件 0 次** |

**根本原因**：Victoria 3 的 defines 是**数据驱动**的——RTTI 里 60 多个
`CDefineRegistryHelper_NAI...::NDefines` 类就是证据。
`COUNTRY_GDP_CONSTRUCTION_MODIFIER_DIVISOR = 2000000` 这类参数是运行时从
`00_defines.txt` 读进全局结构体的，**没有编译进机器码**。代码里只有
「读 defines 结构体的某个偏移」，靠常量定位计算函数**原理上不可行**。

**教训**：这个引擎里凡是「数值由 defines 控制」的公式，静态分析只能拿到控制流
（哪些变量参与运算），拿不到系数。要系数就查 defines 文件，要公式结构就查本地化。
两者配合已经够用——GDP 实测误差 2.3% 就是这么来的。

### 9.9 `average_productivity` 是什么

**官方公式**（`localization/simp_chinese/concepts_l_simp_chinese.yml:1474`
的 `concept_productivity_desc` 直接写着）：

```
人均年产值 = （商品生产的每周收入 − 商品消费的支出）÷ 总就业人数 × 52
            （收入 − 材料费）/ 就业者总数 × 52
```

说明里还有一句：「它与平均工资的差值就是建筑的每周结余，也就是利润」。
所以它是**每个就业者每年创造多少价值**，不是百分比。

存档里位置是 `budget.average_productivity`，非零 291/735 国，范围 0 ~ 5.23，
大清 1.46952。

**量级验证**（大清 302 栋建筑）：

```
每周利润 2,020,205.8 + 每周工资 2,123,179.7 = 收入−材料费 4,143,385.5/周
×52 = 215,456,000/年
215,456,000 ÷ 1.46952 ≈ 146,570,000  → 约 1.466 亿就业者
```

大清总人口 3.66 亿、劳动力约四成，量级吻合，公式成立。

**defines 的阈值也对上**：`EARNINGS_ABSOLUTE_LOW_THRESHOLD = 3`、
`EARNINGS_ABSOLUTE_HIGH_THRESHOLD = 30`——大清 1.47 < 3，属于低生产率，
符合它自给农业为主的结构。

**内存侧读不到**：`f32` / `f64` / `i64÷1e4` / `i64÷1e5` 四种编码在 `CCountry`
的 0x2638 字节里全部无匹配。原因是它是**按需现算**的：逐建筑算
（收入−材料费）/就业人数×52，再按就业人数加权平均。而**就业人数不落在建筑对象里**
（`CBuilding` 只有 `staffing`，等于等级数，不是人数），而是分散在各 pop 的就业关系上。
要实时值只能从 `pops` 聚合出每建筑就业人数再套公式。
